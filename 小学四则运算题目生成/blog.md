1.1 项目背景

本次结对项目要求开发一个自动生成小学四则运算题目的命令行程序。

传统的四则运算练习题通常需要人工编写，不仅耗费时间，还容易出现题目重复、计算错误等问题。因此，我们希望通过程序自动完成题目生成和答案计算，提高出题效率。

项目还需要支持答案批改，使程序不仅能够生成练习题，还能够根据用户提交的答案统计正确和错误的题目。

通过本次项目，我们希望进一步掌握命令行程序开发、模块化设计、Git 协作、软件测试以及性能分析的基本方法。

1.2 项目需求

根据作业要求，程序需要完成以下功能：

使用 -n 参数控制生成题目的数量。

使用 -r 参数控制题目中的数值范围，缺少参数时给出错误提示。

保证减法运算过程中不产生负数。

保证除法子表达式的计算结果为真分数。

每道题目最多包含三个运算符。

避免生成符合题目定义的重复题目。

将题目与标准答案分别保存到指定文本文件。

支持一次生成10000道题目。

支持读取题目和答案文件，完成自动批改并统计结果。

其中，题目生成的正确性、去重规则以及分数运算是本次项目的主要实现难点。

3.2 表达式二叉树设计

本项目的一个主要难点是如何表示包含括号和多种运算符的表达式。

如果直接使用字符串拼接生成题目，会遇到两个问题：一是难以判断运算优先级，二是无法准确识别通过交换律产生的重复题目。

因此，项目采用表达式二叉树来表示算式。

在表达式树中，叶子节点保存操作数，内部节点保存运算符。每个节点还记录该子表达式的计算结果。
GitHub
+1

例如，表达式：

3 + 2 × 4

其根节点为加法，左子树是数值3，右子树表示乘法表达式 2 × 4。

通过递归计算子树，可以得到整个表达式的结果。

这一设计使我们能够在生成题目的同时检查每个子表达式的计算结果，而不必等到整道题生成后再重新解析。

3.3 运算规则处理

题目要求减法不能产生负数，除法的结果必须满足指定的分数规则。

在生成过程中，我们对每一个运算节点进行检查。

对于减法，如果左子树的结果小于右子树的结果，就交换左右子树，避免产生负数。

对于除法，首先检查除数是否为零，再计算商。如果结果不符合分数要求，则尝试交换操作数或重新生成子表达式。

为了防止参数范围过小时程序一直无法生成符合要求的题目，还设置了最大重试次数。超过阈值后，程序会抛出异常，提示当前参数下生成题目失败。
GitHub
+1

3.4 分数计算设计

小学四则运算涉及自然数、真分数和带分数。如果使用浮点数计算，可能产生精度误差。

例如，部分分数无法使用二进制浮点数精确表示。

为避免这一问题，项目使用 Python 标准库中的 Fraction 处理有理数计算。

所有分数在内部统一使用分子和分母表示，输出时再根据数值转换为自然数、普通分数或带分数。
GitHub

例如：

1/6 + 1/8 = 7/24

5/2 = 2’1/2

这样不仅避免了浮点数精度问题，还便于判断两个分数是否具有相同的数学值。

3.5 题目去重设计

去重是本次项目中比较复杂的部分。

题目要求，不允许出现通过有限次交换加法或乘法左右子表达式得到的重复题目。

例如：

3 + 5
5 + 3

这两道题属于重复题目。

但是：

1 + 2 + 3
3 + 2 + 1

按照题目规定的表达式树结构，并不属于重复题目。

因此，不能简单地对数字排序，也不能仅通过题目字符串是否相同来判断重复。

本项目使用表达式树的规范化表示解决这一问题。对于加法和乘法节点，将左右子树的规范化结果按照字典序排列；对于减法和除法，保留原有顺序。

生成规范化字符串后，使用 Python 的 set 集合保存已经出现的题目。

当新题目的规范化结果已经存在时，就放弃该题并重新生成。

这样可以在保留表达式结构的同时，识别交换律意义下的重复题目。
GitHub

四、关键代码说明
4.1 命令行参数处理

主程序使用 argparse 处理用户输入，根据参数判断应该执行题目生成模式还是答案批改模式。

生成模式接收 -n 和 -r 参数，批改模式接收 -e 和 -a 参数。

主程序还需要检查参数是否完整，并防止两种工作模式同时使用。相关逻辑位于 main.py。
GitHub

示例命令：

python main.py -n 10 -r 10

其中，-n 10 表示生成10道题目，-r 10 表示题目中的数值上限为10，不包含10。

执行后，程序会将题目和答案写入对应的文本文件。

4.2 表达式生成与合法性检查

在 generator.py 中，程序通过递归方式构建表达式树。

首先随机确定运算符数量，再将运算符分配到左右子树中。

每个子树生成后，程序根据运算符执行相应的计算和合法性检查。

例如，减法会先比较左右操作数，除法会检查分母与计算结果是否合法。

如果当前表达式无法满足规则，程序就重新尝试生成，直到得到合法表达式或达到重试上限。
GitHub

这种方法将合法性检查放在表达式构建过程中，避免先生成大量非法题目再统一筛选。

4.3 规范化去重

在 tree.py 中，canonical_repr() 函数负责生成表达式树的规范化表示。

核心思想是：对于可以交换的运算符，统一左右子树顺序；对于不能交换的运算符，保留原有顺序。

随后，生成器通过集合判断规范化结果是否已经出现。

代码中的关键逻辑如下。
GitHub

c_repr = tree.canonical_repr()

if c_repr in seen_canonical:
    consecutive_failures += 1

如果发现重复题目，就增加失败计数并重新尝试。

对于不重复的题目，将规范化结果加入集合，再保存题目及答案。

4.4 分数格式转换

fraction_utils.py 负责将内部的 Fraction 对象转换为符合要求的字符串。

格式转换需要考虑三种情况：

当分母为1时，输出自然数；当分子小于分母时，输出普通分数；当分子大于分母且不能整除时，输出带分数。

例如：

Fraction(3, 1)  →  3

Fraction(3, 5)  →  3/5

Fraction(19, 8) →  2’3/8

通过统一的格式化函数，可以避免在题目生成模块和答案输出模块中重复编写分数处理代码。
GitHub

4.5 答案批改

evaluator.py 使用分词与双栈求值的方法，对输入的算术表达式进行解析和计算。

程序先识别数字、运算符和括号，再按照运算优先级计算表达式的结果。

计算完成后，将标准答案和用户答案都转换为 Fraction 对象进行比较。

最后，统计正确和错误的题号，并写入 Grade.txt。

这样可以按照数学数值判断答案，而不是简单比较字符串。
GitHub

五、程序效能分析与优化
5.1 性能分析目的

本项目要求支持一次生成10000道四则运算题目。

随着题目数量增加，随机生成、合法性检查和去重等操作都可能影响程序运行效率。

因此，我们需要分析程序在大规模生成任务下的运行表现，找出主要的时间开销，并确定优化方向。

使用 Python 自带的 cProfile 对程序进行性能分析。

测试命令如下：

其中，cumulative 表示按照函数累计耗时排序。

通过性能分析，可以查看函数的调用次数、自身耗时以及累计耗时，从而定位需要重点优化的代码。

本次重点关注 generate_exercises()、generate_tree() 和 canonical_repr() 等函数。

5.3 性能优化思路

从程序结构来看，题目生成过程中存在三个值得重点关注的环节。

首先是随机生成表达式。每次生成的表达式都需要满足数值范围和运算规则，如果大量表达式不合法，就会增加重复尝试次数。

其次是题目去重。随着已经生成的题目不断增多，程序需要频繁判断新题目是否已经出现。

最后是分数计算。复杂表达式涉及多次分数运算、化简和格式转换，可能产生额外开销。

针对这些问题，项目采用了以下设计思路。

在表达式生成阶段直接进行合法性检查，减少无效题目进入后续处理的机会。

在去重阶段使用规范化字符串和 set 集合，避免对已有题目进行逐个遍历比较。

在计算阶段使用统一的分数工具，减少重复转换，并保证计算精度。

这些设计有助于控制生成过程的时间开销，但具体性能改善程度仍需要通过实际测量确认。

此外，测试和代码复审也占用了较多时间。这些工作虽然不会直接增加新功能，但有助于发现程序中的逻辑问题，提高程序可靠性。

今后在进行类似项目时，我们会更加重视前期需求分析，并在时间计划中为测试和修改预留足够时间。

7.2 项目收获

通过本次结对项目，我们对软件开发流程有了更加完整的认识。

首先，我们体会到了模块化设计的重要性。

如果将参数解析、表达式生成、分数计算和文件输出全部写在一个文件中，代码会变得难以维护。将各功能拆分为独立模块后，可以分别检查和修改，提高开发效率。

其次，我们认识到了数据结构对算法设计的影响。

最初分析题目去重问题时，仅通过比较字符串很难满足要求。采用表达式二叉树后，不仅能够正确表示运算顺序，还能通过规范化表示处理交换律产生的重复题目。

最后，我们对软件测试有了进一步理解。

程序能够正常运行，并不代表它完全满足需求。尤其是在随机生成题目的场景中，部分错误可能只会在特定的运算符组合或参数范围下出现，因此必须设计不同类型的测试用例进行验证。

7.3 存在的问题与改进方向

本项目仍有进一步完善的空间。

首先，题目生成主要依赖随机采样，当数值范围较小或已生成题目较多时，可能出现较多重复尝试，影响生成效率。

后续可以研究更加合理的生成策略，减少无效采样。

其次，虽然已经将主要功能划分为不同模块，但仍需要继续完善自动化测试，提高程序修改后的回归测试效率。

最后，可以进一步优化程序的错误提示和使用说明，让用户更容易理解输入参数的要求，以及题目生成失败的原因。

这些问题也是我们后续改进项目的主要方向。
